# CodeBridge — 「稟議」を再設計するAIエージェント

日本企業の承認フロー（稟議）を**廃止するのではなく、再設計する**AIエージェントシステム。AIが変更案を生成・検証し、人間が最終承認する——その「責任分界点」を設計することをコンセプトに開発しました。**Microsoft Agent Hackathon** 提出作品です。

> **🟢 現在は DEMOモードで公開中（ポートフォリオ用・課金0円）**
> ハッカソン終了に伴い Azure 課金を停止しているため、AI生成ステップはサンプル応答に差し替えています。
> **ログイン → 自然文入力 → 稟議書生成 → 承認** までの全フローは、APIキー無し・無料でそのまま体験できます。
> 実際に Azure OpenAI を動かす場合は `DEMO_MODE=0` を設定してください（[下記参照](#実際にaiを動かす場合)）。
> ※ ライブのAzure環境（旧本番URL `https://codebridge-ringi.azurewebsites.net`）は停止済みです。

---

## 🎯 背景 — なぜ稟議を「再設計」するのか

日本企業の意思決定は、現場の要望 → エンジニア → ベンダー発注という構造で、反映までに数週間〜数ヶ月かかることがあります。稟議そのものも、**約半数（50.5%）が「3日以上かかる」**、最多の悩みは**「承認までに時間がかかる」（60.5%）**と報告されています（株式会社エイトレッド調査）。

一方で、稟議の本来の価値——**合意形成・監査証跡・責任の明確化・周知**——は失ってはいけません。そこで CodeBridge は「稟議廃止」ではなく、承認を次の2つに分け、AIと人間の役割を設計し直します。

| 承認の種類 | 求められること | 担い手 | 割合の目安 |
|---|---|---|---|
| **確認型承認** | 規則・基準の確認 | AIが補助 | 約8割 |
| **判断型承認** | 文脈・リスクの読解 | 人間が集中 | 約2割 |

> **核心**: 「AIが勝手にシステムを変えた」状況が構造上発生しないよう、**実行は必ず人間の承認後**に行います。

## 🧩 3つのフェーズ

| フェーズ | 内容 |
|---|---|
| **Phase 1 — 承認型コード変更** | 自然言語の指示でHTMLを修正。サンドボックス検証後、**エンジニア承認を経て反映** |
| **Phase 2 — 稟議フロー統合** | 申請内容から稟議原稿の生成・承認者の推薦・承認タイプの自動判定 |
| **Phase 3 — 意思決定ログ分析** | 滞留申請・ボトルネック承認者・自動化できる確認型承認を可視化 |

### 責任設計のフロー
```
担当者が変更を依頼
    ↓
AIが変更案を生成（変更量を最小化）
    ↓
サンドボックスで検証（最大3回の自己デバッグ）
    ↓
エンジニアに「差分・レポート・検証結果」を提示
    ↓
エンジニアが承認
    ↓
反映 + 監査ログ保存
```

## ✨ 主な機能

| 機能 | 概要 |
|---|---|
| 🤖 **稟議書の自動生成** | 自然文の申請から、タイトル・理由・変更内容・想定リスク・確認ポイントをAIが起案 |
| 🏷 **承認タイプの自動判定** | 確認型／通知型／判断型／合議型を分類し、通知先・トーン・エスカレーションを判断 |
| 👤 **承認者のAIレコメンド** | 役職・役割から最適な承認者を提案（理由つき） |
| ✅ **承認フロー** | 承認 / 差し戻し / 再生成（フィードバックを反映して作り直し） |
| 🛠 **コード変更の自動反映** | HTML修正をAIが生成→検証→**承認後に**自動適用。`/demo` でリロード即反映 |
| 🔁 **自己デバッグループ** | 生成→検証→エラー分類→修正を最大3回自動実行 |
| 📊 **意思決定ログ分析** | 申請統計・承認の遅延・ボトルネック承認者・自動化候補を可視化 |
| 💰 **コスト透明性** | リクエスト単位でトークン数・コストを記録し管理画面に表示 |
| 🔐 **ロールと責任設計** | Requester / Engineer / Admin で権限を分離、全承認を監査ログに記録 |

### 承認タイプの判定基準

| タイプ | 判定基準 | 処理 |
|---|---|---|
| **確認型** | 規定内・前例あり・低リスク | AIが確認ポイントを整理、記録のみ |
| **通知型** | 情報共有・決定不要 | 自動通知・ワンクリック確認 |
| **判断型** | 例外・高額・新規・リスクあり | 個別通知・期限付き |
| **合議型** | 組織横断・契約・重要投資 | 複数承認者へ並列／直列通知 |

### ロールと権限

| ロール | 権限 |
|---|---|
| **Requester（申請者）** | 指示送信のみ・コードは非表示 |
| **Engineer（承認者）** | 差分確認・承認・差し戻し・コスト閲覧 |
| **Admin（管理者）** | 全機能 + ユーザー管理 + 監査ログ |

## 🧱 技術スタック

| 層 | 技術 | 選定理由 |
|---|---|---|
| フロントエンド | HTML / CSS / Vanilla JS | 依存ゼロ・即時反応・モバイル対応 |
| バックエンド | FastAPI（Python 3.11） | 高速・型安全・OpenAPI自動生成 |
| 実行環境 | Azure App Service（West US 2） | 常時起動・HTTPS・SPA配信 |
| AI | Azure OpenAI o4-mini | 推論品質・コスト・Azure統合 |
| 認証 / データ | JWT + SQLite | 軽量・移行容易・PoC適合 |
| サンドボックス | Python subprocess + html.parser | 外部依存ゼロ・日本語対応 |
| ログ・コスト | SQLite | 永続化・CSV出力・リアルタイム閲覧 |

### アーキテクチャ
```
ブラウザ（SPA: frontend/index.html）
        │  REST / JWT
        ▼
FastAPI（api_main.py）
   ├─ core/auth.py               認証・DB操作（SQLite）
   ├─ core/ringi_orchestrator.py  稟議書をAI起案（Azure OpenAI）
   ├─ core/orchestrator.py       コード変更パイプライン（自己デバッグ）
   ├─ core/sandbox.py            生成HTMLの安全な検証・適用
   └─ core/azure_client.py       Azure OpenAI クライアント（★課金経路の集約点）
```

申請の分析もコード変更パイプラインも、AI呼び出しはすべて `core/azure_client.py::_call()` に集約。`DEMO_MODE` はこの1点を含めて確実に塞ぐ設計です。

## 🔐 セキュリティ設計

- AIは本番DBに直接アクセスしない（修正対象は専用コピーのみ）
- 反映前に自動バックアップ
- 差分・レポート・検証結果を承認者に提示してから反映
- すべての承認を監査ログに記録

> 本リポジトリは「本番品質」ではなく、**“どこに責任の境界を置くべきか検証できる構造”** を優先したPoCです。

## 実際にAIを動かす場合

DEMOモードを切り、Azure OpenAI のキーを設定します。

```bash
# .env
DEMO_MODE=0
AZURE_OPENAI_API_KEY=...
AZURE_OPENAI_ENDPOINT=https://<your-resource>.openai.azure.com/
AZURE_OPENAI_DEPLOYMENT=o4-mini
```

`DEMO_MODE=1`（デフォルト）のあいだは Azure OpenAI を一切呼ばず、課金は発生しません。
